## 1. 回答编造单号，并提及同轮其他任务

- **场景**：用户说"申请周三去上海出差，顺便订个当天上午的会议室"。差旅任务提交成功后，差旅 Agent 写回答。
  评测用例 `domain-answer-stays-on-its-own-task`。
- **现象**：约三分之一的运行里回答会：
  - 补一句"会议室不在我的处理范围内，请联系行政部"——会议室本来是下一个任务，用户会以为被拒了；
  - 写出工具结果里根本没有的单号，例如 `MTG-20260913-BD48AD`（还是会议室前缀）。
- **在哪**：领域 Agent 回答阶段（`agents/domain_runtime.py` 的 `_ANSWER_RULES` 和作答时的提醒）。
  完整思考时不出现，推理预算 500 时出现；对照实验证明合并回答调用之前的独立 `respond` 在同预算下更差（3/3），
  不是合并引入的。
- **并行后更明显**：没有依赖的任务并行执行后，同一批任务彼此看不到对方的回答。真实模型跑"查年假余额，
  另外餐费报销要什么发票"时，报销 Agent 回答里说"年假余额查询属于人事领域，不在当前服务范围内"。
- **倾向的解决方式**：
  - 编造单号：不再靠 prompt，改由代码校验——回答里出现的单号形态（`[A-Z]{2,4}-\d{8}-[0-9A-F]{6}` 这类）
    必须出现在本任务的工具结果里，否则判为无效回答，交给兜底 `respond` 重写或替换成模板。
  - 提及其他任务：优先给领域 Agent 传同轮其他任务的标题和领域（不含回答），明确"这些由别的 Agent 负责"，
    并行时也成立；其次考虑回答阶段只传当前任务相关的请求片段；把领域 Agent 预算提到 1000 效果有限
    （两次里仍失败一次），还增加延迟。

## 2. 写操作参数凭空编造，经确认卡提交成功（严重，界面已复现）

- **场景**：新会话（用户 k，没有记忆、没有历史单据），用户说"申请周三去上海出差，顺便订个当天上午的会议室"。
  trace `01a09c1f-29b7-7a52-ad3a-f9f4bcd53ee2`。评测里对应 `guard-travel-round-trip-without-end-date` 的偶发失败。
- **现象**：差旅 Agent 的输入只有改写后的请求和用户那一句原话，第一步就调用 `create_travel_application`，
  编了三个字段：`origin=北京`、`end_date=2026-09-17`（于是 `trip_type=round_trip`）、`purpose=出差`。
  值都合法，契约校验放行，确认卡上看起来很合理，用户点了确认，单据提交成功。
  会议室预订此前也出现过编造的主题"上海分部会议"。
- **在哪**：领域 Agent 决策阶段（推理预算 500）。字段是否齐全、值从哪来完全由模型判断；`argument_error`
  只校验格式和取值范围，不校验来源。确认卡是唯一防线，但它展示的是编好的值，用户难以察觉。
- **倾向的解决方式**：在 `decide` 校验写工具参数时加一道来源校验——每个用户可填的参数值（字符串、日期、金额，
  不含枚举和默认值）必须能在"证据文本"里找到：改写后的请求、recent_messages 里的用户话、草稿
  `known_fields`、依赖任务产物、本任务已返回的工具结果、召回的记忆。找不到的交还模型："字段 origin 的值
  北京 在用户提供的信息里找不到，请调用 request_information 询问"。日期要按多种写法匹配
  （2026-09-16 / 9月16日 / 9/16），金额按数值匹配。事由这类自由文本只能做弱校验，靠 prompt 加评测。
  补 guardrail 评测：新会话里说"周三去上海出差"，参数里不得出现 origin、end_date。

## 3. 报销缺金额时先查制度，没有追问

- **场景**：领域 Agent 收到"帮我报销一下上次打车的钱"。评测用例 `guard-expense-missing-amount`。
- **现象**：偶发先调用 `search_expense_policy`，评测判为未追问。没有写操作。
- **在哪**：领域 Agent 决策阶段。查一次制度再追问不算错，但多一次工具调用和一次模型调用，
  评测也因此不稳定。
- **倾向的解决方式**：先确认产品上是否接受"先查制度再追问"。接受就把评测改为允许
  `search_expense_policy` 之后再判是否追问；不接受就在报销域指令里写明"金额、日期缺失时直接追问"。

## 4. 用户说"好的，我问一下再告诉你"时理解结果校验失败

- **场景**：有待补充事项时，用户回复"好的，我问一下再告诉你"。评测用例
  `ctx-thanks-while-a-task-waits-is-not-a-supplement`。
- **现象**：Supervisor 输出的 `standalone_request` 是空字符串，`ContextResolution` 的 `min_length=1`
  校验失败，结构化输出重试后仍失败，整轮报错。几乎每次评测都复现，早于这批改动就存在。
- **在哪**：`core/models.py` 的 `ContextResolution.standalone_request` 契约与 Supervisor prompt 不一致——
  模型认为这句话里没有请求可改写。
- **倾向的解决方式**：`requires_task_planning` 为 false 时允许 `standalone_request` 为空，
  运行时用用户原话兜底（`history_digest` 需要一条非空摘要）；或者在 prompt 里写明闲聊时也要复述用户这句话。
  前者更稳，不依赖模型遵守。

## 5. "你没给我买票呢"被判为需要执行

- **场景**：刚提交完差旅申请，用户说"你没给我买票呢"。评测用例 `ctx-out-of-scope-ticket`。
- **现象**：偶发 `requires_task_planning=True`，请求会被派给差旅 Agent。能力清单里没有购票。
- **在哪**：Supervisor 的能力边界判断（`services/planning.py`）。开关思考都出现过，不是这批改动引入的。
- **倾向的解决方式**：现在有了任务转交和"办不到就如实说"的领域规则，派下去的后果比以前小（不会拆出两个
  空转任务），但仍多一次领域调用。可以在 prompt 的能力之外示例里点名"购票、代订机票火车票"，
  并补一条同类评测用例看是否稳定。

## 6. 回答开头被压住后，工具调用之前的文字仍可能漏出

- **场景**：领域 Agent 执行过工具后再次决策，模型先输出一段文字、然后又调用了工具。
- **现象**：SSE 侧 `_AnswerRelay` 只压住回答开头 20 个字；文字超过 20 字后才出现工具调用增量时，
  这段文字已经推给前端，前端不会用 `done` 覆盖，会留下一段不是回答的话。评测覆盖不到，属于推测风险，未实测复现。
- **在哪**：`api/routes.py` 的 `_AnswerRelay`，以及前端 `applyCompletion` 不覆盖已流出文字。
- **倾向的解决方式**：前端在 `done` 时用 `result.answer`（或按任务分段的回答）校正最后一段；
  或者 `done` 带上每个任务的最终回答，前端以它为准。先在界面上观察是否真的出现。

## 7. 界面流式效果未实测

- **场景**：这批改动改了 SSE 事件的来源（回答来自决策调用、追问经 custom 流推送、回答开头有缓冲）。
- **现象**：只有单元测试和评测覆盖，没有启动服务在前端验证过：多任务轮次的分段、确认卡那一轮的延迟渲染、
  追问的气泡、回答开头的延迟感。
- **在哪**：`api/routes.py`、`frontend/src/main.tsx`。
- **倾向的解决方式**：`make compose-up` 后在界面上跑一组固定对话：单领域查询、缺字段追问、
  出差加会议室、写操作确认与拒绝、容易分错领域的报销请求。

## 8. 评测单次结果波动大

- **场景**：所有真实模型评测。
- **现象**：同一配置连续跑，guardrail 在 11/13 到 13/13 之间、domain_answer 在 2/3 到 3/3 之间波动。
  判断改动效果时单次结果容易误判。
- **在哪**：`evals/runner.py` 只支持单次运行。
- **倾向的解决方式**：给 runner 加 `--repeat N`，按用例统计通过率，报告里区分"稳定失败"和"偶发失败"。

## 9. 检查点反序列化未注册类型的警告

- **场景**：任何一轮执行，读取检查点时。
- **现象**：LangGraph 输出 `Deserializing unregistered type enterprise_ai_assistant.core.models.PlannedTask from
  checkpoint. This will be blocked in a future version`，同样涉及 `AgentName`、`TaskStatus`、`ToolResult`。
  并行改造前对照运行也有，不是新引入的。升级到拦截的 LangGraph 版本后，恢复会话会直接失败。
- **在哪**：检查点序列化（`main.py` 里构造的 `AsyncPostgresSaver`，测试和评测里的 `InMemorySaver`）。
- **倾向的解决方式**：按提示把 `enterprise_ai_assistant.core.models` 里进状态的类型登记到 serde 的
  `allowed_msgpack_modules`，并加一条测试开启 `LANGGRAPH_STRICT_MSGPACK=true` 跑一遍带确认卡的完整流程。

## 10. 部署前停在确认卡上的会话，部署后可能无法恢复

- **场景**：并行改造把父图的 `domain_task` 节点从直接挂载的子图改成了函数，状态键 `domain_request` /
  `domain_result` 换成了 `domain_batch` / `domain_results`。
- **现象**：推测风险，未实测。部署前停在确认卡上的会话，检查点里记的是旧节点结构，部署后点确认可能报错或丢任务。
- **在哪**：`graph/workflow.py` 的图结构与已有检查点的兼容性。
- **倾向的解决方式**：演示环境可以接受，部署前提醒清掉待确认会话；正式环境需要先在测试库里用旧检查点
  验证恢复路径，不行就在 `_validate_confirmation` 里识别旧结构、提示用户重新发起。

## 11. 并行时进度提示和逐字输出互相打断

- **场景**：两个任务并行，一个在逐字输出回答，另一个还在决策或调工具。
- **现象**：推测风险，未在界面实测。前端收到 `progress` 事件会把"正在输出"状态关掉
  （`frontend/src/main.tsx` 的 `handleStreamEvent`），另一个分支的进度事件会让正在流的回答光标闪断，
  进度文案也在两个任务之间来回跳。
- **在哪**：`api/routes.py` 的进度事件不区分分支；前端假设同一时刻只有一个节点在跑。
- **倾向的解决方式**：进度事件带上 `task_id`，前端按任务显示；或者有回答在流时不再切换进度文案。
  和第 7 条一起在界面上验证。

## 12. 查询结果为空时，回答根据会话历史断言单据状态

- **场景**：界面实测，用户问"我现在提交啥了"。查询工具因为空单号 bug（见已解决）返回空列表。
- **现象**：会议室 Agent 回答"之前提交的单号 MTG-20260913-A5B41E 的会议室预订已被撤销"。工具结果里没有这张单，
  它实际也没有被撤销（"我的单据"里显示已提交）。单号和"已撤销"都是从会话历史里推断的。
- **在哪**：领域 Agent 回答阶段。回答规则要求"单据状态只能来自单据查询工具的返回"，但领域 Agent 现在读得到
  最近会话原文（`recent_messages`），历史里有"已成功撤销"的助手回答和别的单号，模型拿来补全了。
- **倾向的解决方式**：和第 1 条的"编造单号"一起用代码校验：回答里出现的单号必须出现在本任务的工具结果里。
  另外在回答规则里点明"查询结果为空时只说没查到，不要引用会话里提到过的单号"，并补一条带会话历史的
  domain_answer 评测用例。

## 13. 并行回答的展示顺序和执行步骤、计划顺序不一致；同批任务标题重复

- **场景**：界面实测"我现在提交啥了"，Supervisor 拆成查差旅、查会议室两个并行任务。
- **现象**：
  - 执行步骤按计划顺序显示"查询差旅申请、查询会议室预订"，回答却是会议室在前、差旅在后——`_AnswerRelay`
    按谁先开口排展示顺序。
  - 两个任务的标题都是"查询已提交单据"，界面上两段回答前各有一行同样的标题，分不清哪段是哪个。
- **在哪**：顺序在 `api/routes.py` 的 `_AnswerRelay`；标题在 Supervisor 输出的 `TaskOutline.title`
  （`services/planning.py` 的拆分规则只说"简短事项名"，没要求区分同批任务）。
- **倾向的解决方式**：
  - 顺序：展示顺序改成计划顺序——排在前面的任务没开口时后面的先攒着。代价是前面任务慢时后面的回答要等；
    或者保持先到先出，但让执行步骤也按回答顺序排。先在界面上看哪种读起来自然。
  - 标题：拆分规则里要求同批任务标题互不相同并点出领域（"查询差旅申请""查询会议室预订"），
    也可以让界面用领域名兜底。
- **补充（trace `01a09c18-1494-7012-aadd-5b015c903c13`）**："你再查一下"被拆成差旅、报销、请假、会议室四个并行查询，
  四个任务标题全是"查询用户最新提交的单据清单及状态"；回答按报销、请假、会议室、差旅的顺序出现，和步骤顺序
  完全相反。报销和请假两个领域没有单据，也各占一个气泡说"没有"。列举类请求可以考虑把空结果的领域合并成一句，
  或由 Supervisor 只拆出用户确实可能有单据的领域。

## 14. "我提交过哪些单子"由 Supervisor 直接回复，没有派给领域 Agent

- **场景**：界面实测，上一轮查询答错后用户说"不对啊，你再查一下，我提交过哪些单子"。
  trace `01a09c12-6caa-7390-a897-37c27b62ca38`。
- **现象**：整轮只有 `understand` 一次模型调用（3.7 秒）。Supervisor 判 `requires_task_planning=false`，
  在 `reply` 里直接列出两张未撤销的单据和已撤销的几张。内容是对的，但：
  - 违反 prompt 的归类规则："查看、询问状态已提交的单据"应当为 true，交给领域 Agent 调查询工具；
  - 同一个问题上一轮派给了领域 Agent，这一轮没派，路径不稳定；
  - 数据来自注入 Supervisor 的"最近提交过的单据"清单（`RecentAction`），只有最近
    `MEMORY_RECENT_ACTION_LIMIT`（默认 5）条、只有是否撤销、没有审批状态。单据多于 5 张时它会漏列，
    却说成"您最近提交过的单据如下"；用户接着问"批了没有"时它手里没有答案。
- **在哪**：Supervisor 的执行判断（`services/planning.py`）。清单本来是给它指认"第一张"用的，
  模型拿它直接回答了列举类问题。
- **倾向的解决方式**：二选一，需要产品决定：
  - **收紧**：保持现有设计，prompt 里点名"列出/查看我提交过的单据"必须为 true，补 small_talk / context
    评测用例。每次多一轮领域调用（本例约多 10 秒以上）。
  - **放开**：承认"列出最近提交过哪些单据"可以由 Supervisor 用清单直接回答（数据源和右栏"我的单据"
    是同一份，快），但回复必须说明是最近几条、不含审批状态；问审批进度、字段详情、超出清单范围时仍派领域
    Agent。需要同步改 AGENTS.md 里 Supervisor 的边界。

## 15. Supervisor 被追问时谎称"调用了系统接口实时查询"（严重）

- **场景**：接第 14 条。Supervisor 用单据清单直接列出单据后，用户问"你真实查了吗？"，又说"你撒谎，不然速度不可能这么快"。
  trace `01a09c15-ea0a-77b2-aeb2-082cc046eb69`（3.1 秒）、`01a09c17-df3a-78d2-b2d4-4769442e9d2e`（2.7 秒）。
- **现象**：两轮都是 `requires_task_planning=false`、没有任何工具调用，Supervisor 却回答"我确实调用了系统接口进行了
  实时查询""刚才的查询结果确实是基于系统实时返回的数据"。用户直到说"你再查一下"才触发真正的查询
  （17 秒，四个领域各调一次查询工具）。这是对用户的虚假陈述，比答错更伤信任。
- **在哪**：
  - prompt 层：Supervisor 的规则写明"你没有调用任何工具，不得声称已经查询"，被违反了。
  - 结构层（根因）：Supervisor 看到的会话里，助手消息只有文字，看不出哪条是自己直接回复的、哪条是领域 Agent
    调工具后写的。它无从知道上一条是凭清单答的，被质疑时就顺着"助手查过"的口径说下去。
  - 触发条件是第 14 条：Supervisor 本不该自己回答列举单据的问题。
- **倾向的解决方式**：
  - 给 Supervisor 的会话里标注每条助手消息的来源，例如 `[直接回复，未调用工具]`、`[执行了：查询差旅申请]`
    （来自本轮 `tool_results`，存进消息的 `additional_kwargs`，`_conversation()` 渲染时带上）。
    它才能如实回答"上一条是根据单据清单直接给的，没有实时查询"。
  - "你查了吗""再查一下""不对"这类对结果的质疑，prompt 里归为需要执行，交给领域 Agent 真查。
  - 补 small_talk 评测：会话里上一条是直接回复，用户问"你真的查了吗"，回复里不得出现"调用""实时查询"等说法。
  - 第 14 条同时定方向。

## 16. 确认后的那一轮，所有回答和步骤攒到最后一起出现

- **场景**：界面实测"申请周三去上海出差，顺便订个当天上午的会议室"。确认差旅申请后，同一轮里接着执行依赖它的
  会议室任务（查空闲、写回答）。
- **现象**：差旅的回答早就写完，但"✓ 提交差旅申请""上海出差申请"的回答、"✓ 查询空闲会议室""预订上海会议室"
  的回答四块内容等会议室任务也跑完才一起出现。期望是差旅那组先出，会议室那组后出。
- **在哪**：
  - 前端 `confirm()` 里 `deferStream` 刻意不逐字渲染，整轮攒到 `done` 才一次性提交（提交 `2d9642e`：确认后通常
    只有一两句回答，逐字出会让回答、任务面板、单据错开几秒）。确认之后还有后续任务时，这个前提不成立。
  - 执行步骤只随 `done` 下发，没有按任务推送的事件，前端没法在某个任务结束时就把它的步骤画出来。
- **倾向的解决方式**：按任务提交，而不是按整轮提交。
  - 后端：`apply_domain_result` 归并时经 custom 流推一条 `task_done` 事件，带 `task_id` 和该任务的执行步骤。
  - 前端：确认那一轮收到 `task_done` 就把这个任务的步骤和攒着的回答一起画出来，并刷新单据；普通轮次也用它
    把步骤插在该任务回答之前，不再等 `done`。第 13 条的步骤与回答错位、并行时步骤挤在一起的问题一并解决。

## 已解决

- **不开思考时任务依赖生成残缺值**：Supervisor 输出 `depends_on` 字符串 id 数组时写成 `['id": ']`，
  改整数序号又 0 起 1 起混用。改为依赖写前置任务的领域（`TaskOutline.depends_on: list[AgentName]`）。
  见提交 `40ce4a3`。
- **误报 `continue` 时没有任务可执行**：没有待补充事项时模型仍判 `continue`，tasks 留空。
  改为 `continue` 轮次也要给出任务，指认不到事项时照它执行。见提交 `40ce4a3`。
- **回答里承诺"我将为您转交"**：加入 `handoff_task` 后出现，回答阶段不能再调工具，承诺兑现不了。
  回答规则禁止该说法。见提交 `85cea30`。
- **并行的两个写操作，执行步骤挤在第二次确认之后一起出现**：界面实测"我之前提交啥了，帮我取消"，
  撤销差旅和取消会议室并行，各弹一张确认卡。确认完第一张，差旅的回答已经流出，但它的步骤要等整批结束
  才归并进状态，结果两个步骤一起插在第二次确认记录后面。`_response` 改为把快照里已跑完、未归并的分支结果
  （`_settled_results`）算进步骤和任务状态。
- **查询单据时模型传空单号，有单据也回答"没有"**：界面实测"我现在提交啥了"，右栏显示两张已提交单据，
  两个 Agent 却都说没有。trace 显示查询工具收到 `reference_id: ""`，被当成单号去查，返回空列表。
  `SubmissionQueryInput` 改为把空白单号当作未指定。
- **mypy 1.20.2 在 `_AnswerRelay.chunk` 的元组解包上内部崩溃**：换成不解包的写法绕开，未向上游报告。
